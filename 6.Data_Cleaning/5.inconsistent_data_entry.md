# 3. Basic Text Normalization

প্রথমে এমন variation fix করতে হবে যেগুলো simple deterministic rule দিয়ে ঠিক করা যায়।

Notebook-এ দুইটি operation ব্যবহার করা হয়েছে:

```python
df['city'] = df['city'].str.lower()
df['city'] = df['city'].str.strip()
```

### `lower()`

Uppercase/lowercase variation remove করে।

```text
Dhaka
DHAKA
dhaka
```

→

```text
dhaka
```

### `strip()`

String-এর শুরু ও শেষের unwanted whitespace remove করে।

```text
' dhaka'
'dhaka '
```

→

```text
'dhaka'
```

### কেন আগে normalization?

কারণ formatting variation-এর জন্য fuzzy matching ব্যবহার করার দরকার নেই।

```text
Raw Text
   ↓
lower()
   ↓
strip()
   ↓
Normalized Text
```

Normalization-এর পরে আবার check করা হয়েছে:

```python
df['city'].nunique()
np.sort(df['city'].unique())
```

Notebook অনুযায়ী normalization-এর পর unique city **42 থেকে 19-এ নেমে আসে**।

> [!IMPORTANT]
> **Basic Text Normalization** simple formatting variation ঠিক করে।  
> **Fuzzy Matching** দরকার হয় remaining spelling/naming variation-এর জন্য।

# 4. Fuzzy Matching

Normalization-এর পরেও কিছু value থাকে যেগুলো দেখতে একই category-এর মতো, কিন্তু exact same নয়।

উদাহরণ:

```text
chittagong
chitagonj
```

Exact matching করলে এরা আলাদা:

```python
'chittagong' == 'chitagonj'
# False
```

Fuzzy Matching string-এর **similarity** measure করে কাছাকাছি candidate খুঁজে বের করতে সাহায্য করে।

সাধারণ ধারণা:

```text
100 → very high similarity
0   → very low similarity
```

তবে score-এর exact meaning কোন **scorer/algorithm** ব্যবহার করা হয়েছে তার ওপর নির্ভর করে।

# 5. Edit Distance ও Levenshtein Distance

Fuzzy matching বুঝতে **Edit Distance** গুরুত্বপূর্ণ।

একটি string-কে অন্য string-এ convert করতে minimum কতটি edit operation দরকার, সেটিই edit distance-এর মূল ধারণা।

### প্রধান operations

| Operation | অর্থ |
|---|---|
| Insert | নতুন character যোগ করা |
| Delete | character মুছে ফেলা |
| Substitute | একটি character অন্যটি দিয়ে replace করা |

উদাহরণ:

```text
cat → cut
```

এখানে `a → u`, তাই একটি substitution।

### Levenshtein Distance

**Levenshtein Distance** হলো একটি নির্দিষ্ট edit-distance measure, যেখানে সাধারণত:

- insertion
- deletion
- substitution

এর minimum সংখ্যা গণনা করা হয়।

> [!IMPORTANT]
> **Fuzzy Matching** = broader matching concept  
> **Levenshtein Distance** = একটি specific distance measure

সব fuzzy scorer শুধু Levenshtein Distance-এর ওপর নির্ভর করে না।

# 6. Similarity Score ও Threshold

Fuzzy matcher candidate-এর সাথে query-এর similarity score দেয়।

উদাহরণ:

```text
query: chittagong
candidate: chitagonj
score: 84
```

Score দেখে বোঝা যায় candidate কতটা similar।

কিন্তু **high similarity ≠ guaranteed same meaning**।

যেমন:

```text
austria
australia
```

দুটি string similar হলেও real-world entity আলাদা।

### Threshold

Threshold হলো minimum acceptable score।

Notebook-এ:

```python
threshold = 70
```

অর্থাৎ:

```text
score >= 70
    ↓
acceptable candidate

score < 70
    ↓
review required
```

> [!WARNING]
> Threshold কোনো universal rule নয়। Notebook-এ `70` ব্যবহার করা হয়েছে matching workflow দেখানোর জন্য। Final project-এ threshold data অনুযায়ী validate করতে হবে।

# 9. Real Fuzzy Matching Workflow

Notebook-এ শুধু একটি sample দিয়ে process বোঝানোর পর পুরো normalized city list-এর ওপর matching করা হয়েছে।

প্রথমে:

```python
normalized_canonical_cities = df['city'].unique()
paired_cities = []
```

তারপর প্রতিটি normalized city-এর জন্য canonical city list থেকে best match:

```python
for city in normalized_canonical_cities:

    match = process.extractOne(
        city,
        canonical_cities,
        scorer=fuzz.ratio
    )

    paired_cities.append({
        'normalized_cities': city,
        'matched_canonical_city': match[0],
        'score': match[1]
    })
```

এরপর DataFrame:

```python
paired_cities_df = pd.DataFrame(paired_cities)
```

এখানে প্রতিটি normalized city-এর সাথে:

- matched canonical city
- similarity score

store করা হয়েছে।

প্রথমে threshold apply না করে score observe করা হয়েছে:

```python
paired_cities_df.sort_values(
    by='score',
    ascending=True
)
```

> [!IMPORTANT]
> আগে **match + score observe**, তারপর threshold decide করা হয়েছে। সরাসরি blind replacement করা হয়নি।

# 10. Accepted Match বনাম Review Required

Threshold:

```python
threshold = 70
```

তারপর vectorized operation দিয়ে:

```python
paired_cities_df['accepted'] = (
    paired_cities_df['score'] >= threshold
)
```

### Accepted matches

```python
accepted_matches = paired_cities_df[
    paired_cities_df['accepted']
].copy()
```

### Review required

```python
review_required = paired_cities_df[
    paired_cities_df['score'] < threshold
].copy()
```

Conceptually:

```text
All Matches
    │
    ├── score >= threshold
    │       ↓
    │   Accepted
    │
    └── score < threshold
            ↓
       Manual Review
```

Low-score values-কে আবার blindly fuzzy-match করলে incorrect mapping হওয়ার risk থাকে।

# 11. Dictionary Mapping ও Replacement

Accepted matches থেকে mapping dictionary তৈরি করা হয়েছে:

```python
mapping = dict(
    zip(
        accepted_matches['normalized_cities'],
        accepted_matches['matched_canonical_city']
    )
)
```

Structure:

```text
normalized value → canonical value
```

তারপর main dataset update:

```python
df['city'] = df['city'].replace(mapping)
```

এখানে গুরুত্বপূর্ণ distinction:

```text
Fuzzy Matching
      ↓
Candidate Identification
      ↓
Validation / Threshold
      ↓
Mapping
      ↓
Replacement
```

> [!IMPORTANT]
> Fuzzy matching নিজে final cleaning নয়। এটি candidate খুঁজে দেয়; accepted candidate-কে mapping-এর মাধ্যমে standardize করা হয়।

# 12. Set Difference: Final Validation

Accepted mapping apply করার পরে কিছু low-score value dataset-এ থেকে যেতে পারে।

Final check হিসেবে notebook-এ **set difference** ব্যবহার করা হয়েছে:

```python
invalid_cities = sorted(
    set(df['city'].unique()) - set(canonical_cities)
)

invalid_cities
```

এখানে:

```text
Current Dataset Cities
        -
Canonical Cities
        =
Invalid / Remaining Cities
```

### Result কী বোঝায়?

- `[]` হলে → dataset-এর সব city canonical list-এর মধ্যে আছে
- কিছু value থাকলে → সেগুলো manually review করতে হবে

যেমন:

```text
['chatgram']
```

এ ধরনের remaining value হলো **edge case**—algorithm confidently handle করতে পারেনি বা domain-specific decision দরকার।

> [!IMPORTANT]
> Final validation-এর উদ্দেশ্য হলো automated cleaning-এর পরে **কোনো non-canonical value বাকি আছে কি না** নিশ্চিত করা।

# 14. কোন `scorer` কখন ব্যবহার করবে?

`fuzz.ratio` সব ধরনের text variation-এর জন্য best choice নয়। কোন scorer ব্যবহার করবে তা নির্ভর করে **strings-এর variation কীভাবে হচ্ছে** তার ওপর। তাই আগে variation-এর ধরন বুঝে তারপর scorer select করা উচিত।

| Scorer | কীভাবে compare করে | বেশি useful যখন |
|---|---|---|
| `fuzz.ratio` | পুরো দুই string-এর character-level similarity দেখে | সাধারণ spelling/character change এবং strings মোটামুটি একই structure-এর হলে |
| `fuzz.partial_ratio` | একটি string-এর সবচেয়ে similar অংশ অন্য string-এর মধ্যে খুঁজে compare করে | একটি string অন্যটির মধ্যে contained/substring হলে, বিশেষ করে extra text থাকলে |
| `fuzz.token_sort_ratio` | String-কে words/tokens-এ ভাগ করে order ignore করে compare করে | একই words আছে, কিন্তু word order আলাদা হলে |
| `fuzz.token_set_ratio` | Common unique tokens-এর ওপর বেশি focus করে; extra/duplicate tokens-এর প্রভাব কম | দুই string-এ একই গুরুত্বপূর্ণ words আছে, কিন্তু extra বা repeated words থাকতে পারে |

## `ratio` — সাধারণ spelling similarity

Character-level structure প্রায় একই এবং spelling/typing error হয়েছে—এমন ক্ষেত্রে `ratio` ভালো starting point।

```text
chittagong
chitagonj
```

এখানে মূল সমস্যাটি character-level spelling variation, তাই `fuzz.ratio` natural choice। Notebook-এর main implementation-এও এই scorer ব্যবহার করা হয়েছে। fileciteturn3file0L271-L300

### কখন `ratio` ব্যবহার করবে?

- typo বা spelling mistake আছে
- string-এর overall structure প্রায় একই
- word order গুরুত্বপূর্ণ নয়, কারণ সাধারণত single-word value
- simple exact-like text variation detect করতে চাও

---

## `partial_ratio` — substring / extra text থাকলে

`partial_ratio` পুরো string-এর পরিবর্তে একটি string-এর মধ্যে অন্যটির সবচেয়ে similar অংশ খুঁজে compare করে। তাই একটি value অন্যটির **part** হলে এটি useful।

```text
chittagong
chittagong city
```

এখানে `chittagong` পুরোপুরি `chittagong city`-এর মধ্যে আছে। এই ধরনের case-এ `partial_ratio` সাধারণ `ratio`-এর চেয়ে বেশি appropriate হতে পারে।

### কখন `partial_ratio` ব্যবহার করবে?

- একটি short value একটি longer string-এর অংশ
- extra prefix/suffix আছে
- product name, title, address বা descriptive text-এর মধ্যে target phrase embedded আছে
- full-string similarity কম হলেও একটি গুরুত্বপূর্ণ অংশ match করা দরকার

### কখন ব্যবহার করবে না?

যদি শুধু ছোট spelling mistake detect করতে চাও এবং দুই string-এর length/structure প্রায় একই হয়, তখন `ratio` বেশি straightforward।

---

## `token_sort_ratio` — word order আলাদা হলে

`token_sort_ratio` string-কে words/tokens হিসেবে দেখে এবং token-এর order normalize করে তারপর similarity compare করে।

```text
south korea
korea south
```

Character order আলাদা হলেও words একই। তাই এখানে token-based comparison বেশি meaningful।

### কখন `token_sort_ratio` ব্যবহার করবে?

- multi-word text আছে
- একই words আছে কিন্তু order বদলে যেতে পারে
- name/title/address-এর word order inconsistent
- spelling-এর চেয়ে token structure বেশি গুরুত্বপূর্ণ

### মূল idea

```text
Original
  ↓
Split into tokens
  ↓
Sort tokens
  ↓
Compare
```

অর্থাৎ `south korea` এবং `korea south`-কে একই token set-এর প্রায় একই arrangement হিসেবে দেখা যায়।

---

## `token_set_ratio` — common words গুরুত্বপূর্ণ হলে

`token_set_ratio` মূলত **common unique tokens**-এর similarity-কে গুরুত্ব দেয়। Extra বা duplicate tokens থাকলেও match score তুলনামূলকভাবে stable থাকতে পারে।

```text
dhaka city
city dhaka
```

অথবা extra/repeated token থাকলে:

```text
dhaka dhaka city
```

যদি মূল meaningful tokens একই হয়, `token_set_ratio` এই ধরনের variation-এর জন্য useful হতে পারে।

### কখন `token_set_ratio` ব্যবহার করবে?

- common words/keywords সবচেয়ে গুরুত্বপূর্ণ
- extra words থাকতে পারে
- duplicate words থাকতে পারে
- token order-ও গুরুত্বপূর্ণ নয়
- tags, names, descriptions বা noisy multi-word text compare করতে হচ্ছে

### `token_sort_ratio` বনাম `token_set_ratio`

দুটিই token-based, কিন্তু focus আলাদা:

```text
Token Sort
→ একই tokens আছে, order normalize করে compare

Token Set
→ common unique tokens-এর overlap বেশি গুরুত্ব পায়
```

অর্থাৎ:

| Situation | Better choice |
|---|---|
| Same words, শুধু order বদলেছে | `token_sort_ratio` |
| Same important words + extra/duplicate words আছে | `token_set_ratio` |
| সাধারণ spelling/character variation | `ratio` |
| এক string অন্যটির অংশ / extra text | `partial_ratio` |

## Practical Scorer Selection Guide

প্রথমে variation-এর ধরন identify করো:

```text
Single-word spelling/typo?
        ↓
      ratio

একটি string অন্যটির অংশ?
        ↓
   partial_ratio

Same words, order different?
        ↓
 token_sort_ratio

Same important words + extra/duplicate tokens?
        ↓
 token_set_ratio
```

### গুরুত্বপূর্ণ সিদ্ধান্ত

Scorer নির্বাচন করার সময় শুধু **highest score কোন scorer দেয়** সেটা দেখবে না। আগে বুঝবে **তোমার data-এর inconsistency-এর pattern কী**। কারণ একই pair-এর জন্য different scorer different score দিতে পারে। তাই scorer + threshold দুটোই context অনুযায়ী select করতে হবে।

> [!IMPORTANT]
> `fuzz.ratio` হলো একটি ভালো **default starting point**, কিন্তু universal solution নয়।
>
> **Single-word spelling issue → `ratio`**  
> **Substring / extra text → `partial_ratio`**  
> **Same words, different order → `token_sort_ratio`**  
> **Common words + extra/duplicate tokens → `token_set_ratio`**
>
> Scorer selection-এর পরও **threshold + validation** প্রয়োজন; high fuzzy score নিজে থেকে semantic equivalence প্রমাণ করে না।
